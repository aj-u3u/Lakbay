Use these labels literally:

- **Verified in code**: a source-level fact only. A UI, route, repository method, or migration does not prove an end-to-end flow.

## Missing or incomplete contracts, ordered by dependency

1. **Shared runtime environment — Needs live Android verification.** Set one reachable API URL for A and M, one backend/database, allowed browser origin, admin and traveler test accounts, and non-secret test records. Read back canonical IDs and response bodies. No live data state was inspected here.
2. **Admin inventory/restore — Verified in code; Needs a product decision.** Public catalog/rate reads omit inactive/unavailable records; repository flags are not exposed in a protected inventory route. Decide whether admin restore is required, then specify auth, filters, pagination, audit/restore semantics. `B:app/features/destinations/router.py:21-64`; `B:app/features/accommodations/router.py:24-46`; `B:app/features/transportations/router.py:24-46`.
3. **Rate money semantics — Verified in code; Needs a product decision.** `price` has no currency, billing basis, validity or verification fields in the catalog models/migration (`B:app/features/accommodations/models.py:26-36`; `B:app/features/transportations/models.py:29-42`). Planning preview accepts explicit traveler assumptions (`B:app/features/planning/schemas.py:56-77`), which are not catalog facts. Decide required units before displaying totals.
4. **Mobile catalog adapter — Verified in code; Needs live Android verification.** Implement paged destination fetch and actual accommodation/transport fetch by stable `destination_id`, parse supported metadata, refresh after admin edits, and distinguish network error/offline demo from current records. `M:lib/services/api_service.dart:467-485`; `M:lib/models/destination.dart:336-441`.
5. **Planning state and cost provenance — Verified in code; Needs a product decision.** Choose whether Android uses `POST /planning/preview` as the authoritative cost/selection preview. Preserve input revision, rate IDs, explicit allowances/units, missing costs, and source labels; do not turn fixed client allowances or AI fallback into verified totals. `B:app/features/planning/schemas.py:93-114,236-302`; `M:lib/services/api_service.dart:828-908`.
6. **Trip reference integrity — Verified in code.** Remove first-destination substitution and attach exact selected destination/activity/rate IDs. Define behavior for unmatched free text and stale/deactivated records before saving. `M:lib/services/api_service.dart:2008-2084`; `B:app/features/trips/models.py:99-205`.
7. **Invitation and PDF actions — Verified in code; Needs a product decision.** Email-based member add and backend PDF exist; link join does not. Choose a true invite-link token flow or remove that action. Connect the PDF button to the existing authenticated PDF endpoint and actual Android file handling. `B:app/features/trips/router.py:178-214`; `B:app/features/reports/router.py:36-58`; `M:lib/screens/trips/trips_screen.dart:230-268`; `M:lib/screens/collaboration/group_dashboard_screen.dart:4150-4189`.
8. **Account/support/review scope — Needs a product decision.** Agree whether password reset/change, support delivery, traveler reviews, and admin-wide users/trips/reviews are capstone requirements. Current UI/route inventory cannot supply those behaviors. Define permission and privacy policy before adding endpoints.
9. **Operational deployment — Needs live Android verification.** Confirm migration head on the real Postgres/PostGIS database, external AI/route/weather/image dependencies, CORS, TLS/cleartext policy, Android runtime permissions, release signing, and app build. Isolated tests do not prove these.

## Ordered implementation checklist and acceptance gates

These are future work items, not claims that Phase 2+ has started. For every slice, keep the existing mobile changes, use one small branch/review unit, add tests for the actual contract, and run the Android acceptance journey.

1. **Baseline and environment.** Record deployment target, API URL, DB migration revision, provider configuration, Android device/emulator, test accounts and seeded IDs. Gate: A and M call the same reachable `/api/v1/health` and catalog; authenticated read works. **Needs live Android verification.**
2. **Truthful destination flow.** Page all active destinations; map canonical fields; show honest loading/error/empty states; remove unmarked demo fallback. Gate: create/update/deactivate one record in A, read its ID via API, and see the same values in M after refresh; deactivated record disappears. **Verified in code gap; Needs live Android verification.**

4. **Planner and AI.** Use server preview/validated AI contracts, preserve all chosen IDs and user-entered allowances, show partial costs and all agreed AI options, then save the selected trip. Gate: reload yields the same destination IDs, itinerary, rate references, planned cost labels, and route; API failure cannot appear as a saved plan. **Needs a product decision; Needs live Android verification.**
5. **Collaboration and expenses.** Keep email member add; decide link-join behavior; verify member roles, task assignment, splits and totals from two accounts. Gate: owner/member permissions and changes survive restart, outsider is denied, and success follows server confirmation. **Needs a product decision; Needs live Android verification.**
