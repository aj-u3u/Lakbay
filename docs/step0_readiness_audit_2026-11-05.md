## Routing finding

The local configuration uses `https://router.project-osrm.org` for both driving and walking, changing only the URL profile segment. A Davao sample query from `125.41528,7.18498` to `125.42000,7.18300` returned the same **552.7 m / 116.3 s** through `/route/v1/driving/...` and `/route/v1/walking/...`, including identical waypoint snap distances. This is evidence that the configured public endpoint is not serving a distinct walking calculation. OSRM's graph is chosen when OSM data is extracted with a profile; the URL segment alone is not a separate foot network. See the [OSRM profile documentation](https://github.com/Project-OSRM/osrm-backend/blob/master/docs/profiles.md) and [HTTP API documentation](https://github.com/Project-OSRM/osrm-backend/blob/master/docs/http.md).

The route service falls back to labeled Haversine estimates if OSRM fails. It must not present an estimated route as turn-by-turn directions. With zero verified arrival points, current routes may terminate at an attraction pin rather than a reviewed visitor entrance; the response already distinguishes `coordinate_basis=attraction` from `verified_arrival`.
